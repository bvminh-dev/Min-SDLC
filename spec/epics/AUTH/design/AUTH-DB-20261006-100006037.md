Bám ADR-003 (PostgreSQL, Prisma Migrate) và ADR-004 (session phía server, kho phiên trong PostgreSQL). Thời gian là `timestamptz` (UTC). Mọi bảng của AUTH nằm trong module `auth`. Khóa ngoại của AUTH chỉ trỏ giữa bốn bảng dưới đây; tham chiếu của module khác tới `users` là việc của họ (ORD, USR, CRT, CHK... có FK `users`). Bảng dùng chung của platform (PRJ) mà AUTH ghi cùng giao dịch qua service công khai, không FK và không đọc trực tiếp (SB-35): `audit_logs` (AuditLog, ADR-021), `outbox_events` (OutboxEvent, ADR-011), bảng đếm giới hạn tần suất (ADR-014).

Các cột lockout, thu hồi phiên, `used_at` đã nằm trong `entities.md` (E-05); `full_name` (khi USR sửa hồ sơ), `phone`, `avatar_url` do USR đặt qua giao diện nội bộ `updateProfile` của AUTH (AUTH là bên duy nhất ghi bảng `users`). Entity có `id`, `created_at`, `updated_at` theo quy ước chung.

## Bảng
| Bảng | Entity | Khóa | Ràng buộc / chỉ mục |
|---|---|---|---|
| users | User | id (uuid) | `email` citext NOT NULL, unique (không phân biệt hoa thường; ứng dụng vẫn chuẩn hóa chữ thường), CHECK length(email) <= 254; `email_verified_at` timestamptz NULL; `password_hash` text NOT NULL (argon2id kèm salt, m=19 MiB, t=2, p=1 theo ADR-015, tham số trong cấu hình ADR-007); `role` enum user_role NOT NULL default customer (customer, staff, admin); `full_name` text NOT NULL CHECK length 1..100; `phone` text NULL và `avatar_url` text NULL (do USR ghi qua `updateProfile`); `status` enum user_status NOT NULL default active; `failed_login_count` int NOT NULL default 0 CHECK >= 0; `last_failed_login_at` timestamptz NULL; `locked_until` timestamptz NULL; `locked_reason` enum lock_reason NULL (too_many_attempts, admin); created_at, updated_at timestamptz NOT NULL; CHECK ((status = 'locked') OR (locked_until IS NULL AND locked_reason IS NULL)); CHECK (locked_reason IS DISTINCT FROM 'admin' OR locked_until IS NULL); index (role, status) cho kiểm admin cuối cùng; index (created_at DESC, id DESC) cho danh sách admin; index text_pattern_ops trên lower(email) cho tìm tiền tố |
| sessions | Session | id (uuid) | FK users (cột user_id, NOT NULL, ON DELETE RESTRICT); `token_hash` char(64) NOT NULL, unique (sha256 hex của token 256 bit; không lưu token thô); `status` enum session_status NOT NULL default active; `created_at` timestamptz NOT NULL; `last_seen_at` timestamptz NOT NULL; `expires_at` timestamptz NOT NULL (hạn trượt: last_seen_at + 30 phút); `absolute_expires_at` timestamptz NOT NULL (created_at + 7 ngày); `revoked_at` timestamptz NULL; `revoked_reason` enum session_revoke_reason NULL (logout, password_changed, admin_lock, replaced); CHECK ((status = 'revoked') = (revoked_at IS NOT NULL)); CHECK (expires_at <= absolute_expires_at); index (user_id, status); index (expires_at) WHERE status = 'active' cho job dọn |
| password_reset_tokens | PasswordResetToken | id (uuid) | FK users (cột user_id, NOT NULL, ON DELETE RESTRICT); `token_hash` char(64) NOT NULL, unique; `status` enum token_status NOT NULL default issued; `expires_at` timestamptz NOT NULL (created_at + 30 phút); `created_at` timestamptz NOT NULL; `used_at` timestamptz NULL; CHECK ((status = 'used') = (used_at IS NOT NULL)); unique index (user_id) WHERE status = 'issued' (tối đa một token đang sống mỗi user); index (expires_at) WHERE status = 'issued' |
| email_verification_tokens | EmailVerificationToken | id (uuid) | FK users (cột user_id, NOT NULL, ON DELETE RESTRICT); `token_hash` char(64) NOT NULL, unique; `status` enum token_status NOT NULL default issued; `expires_at` timestamptz NOT NULL (created_at + 24 giờ); `created_at` timestamptz NOT NULL; `used_at` timestamptz NULL; CHECK ((status = 'used') = (used_at IS NOT NULL)); unique index (user_id) WHERE status = 'issued'; index (user_id, created_at DESC) cho đếm số lần gửi lại trong giờ |

Bộ đếm tần suất theo IP/email (SB-14 bậc A) là bảng PostgreSQL UNLOGGED của platform (ADR-014), AUTH gọi service giới hạn của platform, không có bảng riêng ở đây. Audit không nằm ở đây: AuditLog thuộc PRJ, AUTH ghi bằng `AuditService.record(tx, ...)` (ADR-021).

Mã `token_hash` là sha256 của token ngẫu nhiên 256 bit (đủ entropy nên không cần băm chậm, ADR-015); khác với mật khẩu (argon2id có salt).

## Trạng thái hợp lệ
Khớp đúng tập trạng thái trong "Vòng đời chi tiết" của `entities.md`. `session_status` là enum riêng; `token_status` dùng chung cho hai bảng token.

| Entity | Trạng thái | Ràng buộc |
|---|---|---|
| User | active | enum user_status; trạng thái khởi tạo |
| User | locked | enum user_status; CHECK nhất quán với `locked_reason`, `locked_until` |
| Session | active | enum session_status; trạng thái khởi tạo |
| Session | revoked | enum session_status; trạng thái cuối, kèm `revoked_at` |
| Session | expired | enum session_status; trạng thái cuối (do job dọn, tính hợp lệ luôn kiểm theo thời gian lúc đọc) |
| PasswordResetToken | issued | enum token_status; trạng thái khởi tạo |
| PasswordResetToken | used | enum token_status; trạng thái cuối, kèm `used_at` |
| PasswordResetToken | expired | enum token_status; trạng thái cuối (quá hạn, hoặc bị thay bằng token mới) |
| EmailVerificationToken | issued | enum token_status; trạng thái khởi tạo |
| EmailVerificationToken | used | enum token_status; trạng thái cuối, kèm `used_at` |
| EmailVerificationToken | expired | enum token_status; trạng thái cuối (quá hạn, hoặc bị thay khi gửi lại) |

## Giao dịch và khóa
Chuyển trạng thái chỉ theo bảng dưới (P5, SB-24); mọi `UPDATE` có điều kiện trạng thái cũ để chuyển chạy đua chỉ thành công một lần. Cột "Event" nói event nào ghi vào `outbox_events` **cùng giao dịch** (ADR-011, SB-27); riêng hai event mang token thô phát in-process sau commit.

| Entity | Từ | Sang | Tác nhân | Event |
|---|---|---|---|---|
| User | (mới) | active | đăng ký email mới (REG) | UserRegistered (outbox) |
| User | active | locked | 5 lần sai (LOGIN, `too_many_attempts`), hoặc admin khóa (LOCK, `admin`) | UserLocked (outbox) |
| User | locked | active | hết hạn khóa tạm (kiểm khi đăng nhập), hoặc admin mở khóa | không (UserUnlocked ở backlog, V-16) |
| Session | (mới) | active | đăng nhập, hoặc `changePassword` cấp phiên mới (đăng ký không tạo phiên) | không |
| Session | active | revoked | logout, password_changed (đặt lại và `changePassword`, mọi phiên), admin_lock, replaced (đăng nhập thay phiên của request; `changePassword` cho phiên của request) | SessionRevoked (outbox) |
| Session | active | expired | job dọn mỗi giờ | không |
| PasswordResetToken | (mới) | issued | FORGOT | PasswordResetRequested (in-process sau commit, best-effort) |
| PasswordResetToken | issued | used | RESET thành công | PasswordChanged (outbox) |
| PasswordResetToken | issued | expired | quá hạn, hoặc FORGOT mới | không |
| EmailVerificationToken | (mới) | issued | REG (email mới), RESEND | EmailVerificationRequested (in-process sau commit, best-effort) |
| EmailVerificationToken | issued | used | VER thành công | EmailVerified (outbox) |
| EmailVerificationToken | issued | expired | quá hạn, RESEND, hoặc VER thành công làm các token còn lại hết hiệu lực | không |

1. **Đăng ký (REG)**: luôn băm mật khẩu trước (cùng chi phí cho email mới và email đã có, để cân thời gian, SB-02). Một giao dịch: `INSERT users ... ON CONFLICT (email) DO NOTHING RETURNING id`; nếu có hàng trả về thì `INSERT email_verification_tokens` và `INSERT outbox_events` (UserRegistered); nếu không có hàng (email đã có, kể cả chạy đua) thì không ghi gì thêm. Cả hai nhánh trả 202 cùng thân. Không tạo `sessions`. Sau commit (chỉ nhánh email mới) phát EmailVerificationRequested in-process. Chuẩn hóa email trước khi insert. Hai yêu cầu cùng email đồng thời: unique làm một yêu cầu không chèn được (ca biên REG), vẫn 202.
2. **Đăng nhập (LOGIN)**: đọc user theo email; nếu không có, vẫn băm so với một băm giả có cùng tham số (cân thời gian). Đăng nhập sai tăng bộ đếm **nguyên tử**: `UPDATE users SET failed_login_count = CASE WHEN last_failed_login_at < now() - interval '15 minutes' THEN 1 ELSE failed_login_count + 1 END, last_failed_login_at = now() WHERE id = $1 RETURNING failed_login_count`; khi giá trị trả về đạt 5, `UPDATE users SET status = 'locked', locked_reason = 'too_many_attempts', locked_until = now() + interval '15 minutes' WHERE id = $1 AND status = 'active'` và chỉ lần cập nhật có hàng bị đổi mới ghi OutboxEvent UserLocked cùng audit (actor_role `system`) trong giao dịch đó (nên chạy song song vẫn một event). Đăng nhập đúng: nếu `status = 'locked'` và `locked_reason = 'too_many_attempts'` và `locked_until <= now()` thì chuyển về `active` (điều kiện trong câu UPDATE); nếu vẫn đang khóa thì trả 401 chung; thành công thì đặt `failed_login_count = 0`, nếu tham số argon2id lưu trong `password_hash` khác cấu hình hiện hành thì băm lại và ghi `password_hash` mới (SB-01), tạo phiên mới và thu hồi phiên cũ của request (`replaced`) trong cùng giao dịch, ghi audit đăng nhập thành công và OutboxEvent SessionRevoked cho phiên bị thay.
3. **Phiên (SESSION)**: kiểm hợp lệ mỗi request bằng `SELECT s.*, u.role, u.status, u.email_verified_at FROM sessions s JOIN users u ... WHERE s.token_hash = $1 AND s.status = 'active' AND s.expires_at > now() AND s.absolute_expires_at > now()`; kết quả dựng `SessionContext {user_id, role, email_verified}` cho guard của platform (ADR-012). Gia hạn: `UPDATE sessions SET last_seen_at = now(), expires_at = LEAST(now() + interval '30 minutes', absolute_expires_at) WHERE id = $1 AND last_seen_at < now() - interval '1 minute'` (bỏ qua nếu mới ghi trong một phút). Role luôn lấy từ `users` (`u.role`) mỗi request, không lưu trong phiên (đổi role hiệu lực ngay). `u.status = 'locked'` coi như không có phiên (401).
4. **Thu hồi nhiều phiên** (reset mật khẩu, admin khóa): `UPDATE sessions SET status = 'revoked', revoked_at = now(), revoked_reason = $r WHERE user_id = $1 AND status = 'active' RETURNING id` trong cùng giao dịch với đổi mật khẩu hoặc khóa; từng `id` trả về là một OutboxEvent SessionRevoked cùng giao dịch.
5. **Token (VER, RESET)**: tiêu thụ bằng `UPDATE ... SET status = 'used', used_at = now() WHERE token_hash = $1 AND status = 'issued' AND expires_at > now() RETURNING user_id`; không có hàng thì trả 400 `invalid_or_expired_token` (bao gồm sai, đã dùng, quá hạn). Hai yêu cầu cùng token: chỉ một có hàng trả về. Với RESET, nếu mật khẩu mới vi phạm chính sách thì kiểm **trước** UPDATE nên không tiêu thụ token. Token của user bị admin khóa không dùng được: RESET kiểm thêm `users.status` trong cùng giao dịch và đảo giao dịch (không tiêu thụ) nếu bị khóa kiểu `admin`. RESET thành công chỉ đặt `failed_login_count = 0`, **không** đổi `status`, `locked_until`, `locked_reason` (khóa tạm tự hết theo thời gian; `locked -> active` chỉ do hết hạn hoặc admin mở, theo `entities.md`).
6. **Phát hành token mới (FORGOT, RESEND)**: một giao dịch: `UPDATE ... SET status = 'expired' WHERE user_id = $1 AND status = 'issued'` rồi `INSERT` token mới (chỉ mục unique một-token-sống bảo vệ chạy đua). RESEND kiểm cooldown 60 giây và tối đa 5 mỗi giờ bằng `created_at` của bảng `email_verification_tokens` (đếm hàng trong giờ, hàng mới nhất trong 60 giây) trong cùng giao dịch, khóa dòng `users` (`SELECT ... FOR UPDATE`) để hai lần bấm đồng thời chỉ qua một. FORGOT giới hạn theo email (5 mỗi giờ) tương tự bằng đếm `password_reset_tokens` trong giờ. Token thô sinh ra chỉ giữ trong bộ nhớ tới khi phát event, không ghi log, không ghi CSDL, không ghi outbox (K-14).
7. **Đổi role (USERADM) và khóa admin (LOCK)**: giao dịch khóa `SELECT id FROM users WHERE role = 'admin' AND status = 'active' FOR UPDATE` (mọi admin đang hoạt động, theo thứ tự id để tránh deadlock) rồi kiểm sau thao tác còn ít nhất một admin `active` (SB-29); vi phạm thì hủy giao dịch và trả 409 `last_admin`. Cập nhật có điều kiện (`WHERE id = $1 AND role = $cũ`). Đây là chỗ duy nhất cần khóa mức hàng cho một tập (không dùng khóa toàn bảng).
8. **Danh sách người dùng (USERADM)**: phân trang offset `page`/`limit` (ADR-006), sắp xếp `created_at DESC, id DESC` ổn định; lọc theo `role`, `status`; tìm tiền tố `lower(email) LIKE lower($q) || '%'` (tham số hóa, SB-11; ký tự `%` và `_` trong `q` được escape). Đếm tổng bằng `COUNT(*)` cùng điều kiện lọc.
9. **Audit** (SB-19, SB-07, ADR-021): mỗi sự kiện đăng nhập thành công, khóa tạm, đặt lại mật khẩu, đổi role, khóa/mở khóa ghi một bản ghi AuditLog **trong cùng giao dịch** bằng `AuditService.record(tx, {actor_id, actor_role, action, target_type, target_id, before, after, reason, correlation_id})` của platform. `actor_role` = `system`, `actor_id` rỗng cho khóa tạm (hệ thống tự khóa). Không ghi mật khẩu, token, lý do khóa ra log thường (SB-18). AuditLog là bảng chỉ thêm (trigger chặn UPDATE, DELETE, SB-32) thuộc PRJ.
10. **Phát event (ADR-011)**: event ghi `outbox_events` cùng giao dịch với thay đổi trạng thái, relay (job của platform) giao at-least-once, thứ tự theo `aggregate_id`; consumer (NTF) chống trùng theo `event_id`. Phong bì `event_id`, `occurred_at`, `correlation_id`. Ngoại lệ K-14: EmailVerificationRequested và PasswordResetRequested mang token thô nên phát in-process sau commit, best-effort (mất thì khách bấm gửi lại), không qua outbox, không log.
11. **Job dọn mỗi giờ** (ADR-013, ADR-022): `UPDATE sessions SET status = 'expired' WHERE status = 'active' AND (expires_at <= now() OR absolute_expires_at <= now())`; `UPDATE ..._tokens SET status = 'expired' WHERE status = 'issued' AND expires_at <= now()`. Xóa phiên và token `revoked`/`used`/`expired` quá 30 ngày (hạn AUTH chốt ở thiết kế này, theo ADR-022 các hạn còn lại do epic chốt). Job này là hạ tầng của AUTH, không phải đồng hồ nghiệp vụ.
12. **Giao diện nội bộ đọc/ghi** (bảng giao diện module, không HTTP): `getUserContact(user_id)` đọc `users` (email, họ tên, `email_verified_at`, `status`) cho NTF; `listActiveUserIdsByRole(role)` đọc `users` theo `(role, status)` cho NTF; `getDisplayNames(user_ids)` đọc `full_name`, `avatar_url` theo lô cho REV (R-27); cho USR: `updateProfile(user_id, {full_name, phone, avatar_url})` ghi ba cột đó, `getUser`, `findCustomerById`, `findCustomerByEmail` (thêm điều kiện `role = 'customer'`), `listAvatarUrlsInUse()` (`SELECT avatar_url ... WHERE avatar_url IS NOT NULL`), `countCustomers()` (`COUNT(*)` với `role = 'customer'`), đều không `tx` (M-01, R-25). `changePassword(user_id, session_id, current, new)` là giao dịch của AUTH (M-12, SB-03): `SELECT ... FOR UPDATE` dòng `users`, kiểm mật khẩu cũ, `UPDATE password_hash`, `UPDATE sessions SET status = 'revoked', revoked_at = now(), revoked_reason = CASE WHEN id = $session_id THEN 'replaced' ELSE 'password_changed' END WHERE user_id = $1 AND status = 'active'` (thu hồi **mọi** phiên kể cả của request), `INSERT` Session mới, `AuditService.record(tx, ...)`, OutboxEvent PasswordChanged và một SessionRevoked mỗi phiên bị thu hồi; không đổi `status`, bộ đếm đăng nhập sai hay hạn khóa. Chỉ `changePassword` phát event.

## Migration
1. Cài extension `citext`; tạo enum `user_role`, `user_status`, `lock_reason`, `session_status`, `session_revoke_reason`, `token_status` (SQL thô trong migration Prisma vì Prisma chưa biểu diễn đủ citext, partial unique index).
2. Tạo `users`, rồi `sessions`, `password_reset_tokens`, `email_verification_tokens` kèm CHECK, unique, partial index ở trên.
3. Không có dữ liệu mồi trong migration. Admin đầu tiên tạo bằng lệnh seed ngoài migration dùng biến môi trường (email, mật khẩu một lần), không có mật khẩu mặc định (SB-16, SB-29, R-03); lệnh seed thuộc khởi tạo của PRJ, ghi `users` qua service của AUTH và băm argon2id.
4. Rollback: bỏ bảng theo thứ tự ngược (token, sessions, users) rồi enum. Chỉ an toàn khi chưa có người dùng thật; sau đó chỉ tiến (forward-only), sửa bằng migration mới.
5. Thêm giá trị enum sau này (ví dụ lý do thu hồi mới) là migration `ALTER TYPE ... ADD VALUE` kèm sdlc-impact. Cột profile (`phone`, `avatar_url`) tạo sẵn ở đây vì `entities.md` ghi chúng là thuộc tính của User; USR chỉ ghi qua `updateProfile` (ba cột `full_name`, `phone`, `avatar_url`), không tạo bảng User thứ hai.
