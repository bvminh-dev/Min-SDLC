Bám ADR-006: REST JSON `/api/v1`, lỗi `application/problem+json` kèm `trace_id`. Thiết kế dựa trên requirement `draft` (skill đòi `approved`, đã được phép chạy trên `draft`).

## Endpoint
Cột Role: role được gọi. Mọi endpoint của DSH chỉ cho `admin` (staff 403: roles.md, SB-07). Mọi endpoint chỉ đọc (GET), cần đăng nhập nên có 401 và 403; mọi endpoint chịu giới hạn 30 yêu cầu mỗi phút mỗi admin (429) và có thể trả 503 khi module nguồn lỗi. Một endpoint gắn một requirement. Không có endpoint nào cho DSH-REQ-20261006-105126549 vì đó là quy tắc chung áp cho cả chín endpoint (xem mục Hợp đồng dữ liệu, "Quy tắc chung").

## Hợp đồng dữ liệu
**Quy tắc chung** (DSH-REQ-20261006-105126549):
- Mọi phản hồi 200 có `as_of` (ISO 8601 UTC, thời điểm đọc nguồn; nội dung từ bộ nhớ đệm giữ nguyên `as_of` cũ). Tiền là số nguyên VND (không số thực). Tên trường snake_case.
- `from`, `to`: chuỗi `YYYY-MM-DD` hợp lệ theo lịch, múi giờ `Asia/Ho_Chi_Minh`, gồm hai đầu; mặc định 30 ngày qua (hôm nay trừ 29 ngày tới hôm nay). Quy tắc: `from` <= `to`, `to` không sau hôm nay, tối đa 366 ngày. Phản hồi luôn lặp lại `from`, `to` đã dùng. Một trong hai tham số có mà thiếu tham số kia thì thiếu tham số nhận giá trị mặc định tương ứng (`to` mặc định hôm nay; `from` mặc định `to` trừ 29 ngày).
- Tham số lạ (ngoài danh sách của endpoint) là 400. Mọi phản hồi 400 có `type` `urn:ecom:error:invalid-parameter` (URN theo ADR-023, dùng `registerProblem` của PRJ), `status`, `trace_id` và mảng `errors` mỗi phần tử có `field`, `reason`.
- 503: `{ "type": "urn:ecom:error:dashboard-source-unavailable", "title": "Dashboard source unavailable", "status": 503, "source": "PAY", "trace_id": "..." }`. `source` là một trong ORD, PRD, INV, USR, PAY. Không có chi tiết nội bộ. Nội dung 503 không được lưu đệm.
- 429: `{ "type": "urn:ecom:error:rate-limited", "status": 429, "trace_id": "..." }` kèm header `Retry-After` (giây). Giới hạn là bậc D của SB-14 (ADR-014): 30 mỗi phút mỗi admin, kho đếm PostgreSQL của platform (ADR-014, M-09; xem DSH-DB).
- 401, 403: dạng chung của PRJ, không có số liệu. Thứ tự kiểm: phiên (401), role (403), giới hạn tần suất (429), tham số (400), bộ nhớ đệm, nguồn (503).

**GET /api/v1/admin/dashboard/revenue** (từ `?from=2026-10-01&to=2026-10-06`):
```json
{ "from": "2026-10-01", "to": "2026-10-06", "as_of": "2026-10-06T03:00:00Z",
  "gross": 670000, "refunded": 200000, "net": 470000, "payment_count": 3,
  "failed_refund_count": 2 }
```
`net` có thể âm. Không giao dịch thì bốn số tiền và đếm đều 0.

**GET /api/v1/admin/dashboard/orders**:
```json
{ "from": "2026-10-01", "to": "2026-10-06", "as_of": "2026-10-06T03:00:00Z",
  "total": 45, "effective": 37,
  "by_status": { "pending": 3, "confirmed": 5, "paid": 12, "shipped": 8, "delivered": 9, "returned": 1, "cancelled": 5, "expired": 2 } }
```
Tám khóa `by_status` luôn có đủ (đúng tám trạng thái Order ở `entities.md`). `effective` = `total` - `cancelled` - `expired` - `returned`.

**GET /api/v1/admin/dashboard/customers**:
```json
{ "from": "2026-10-01", "to": "2026-10-06", "as_of": "2026-10-06T03:00:00Z",
  "total": 1200, "locked": 15, "new_in_range": 37 }
```

**GET /api/v1/admin/dashboard/products**:
```json
{ "as_of": "2026-10-06T03:00:00Z", "total": 143, "by_status": { "active": 120, "draft": 8, "archived": 15 } }
```

**GET /api/v1/admin/dashboard/low-stock**:
```json
{ "as_of": "2026-10-06T03:00:00Z", "count": 7,
  "items": [ { "product_id": "11111111-1111-4111-8111-111111111111", "name": "Tất cổ cao", "sku": "TC-014", "available": 0, "low_stock_threshold": 5 } ] }
```
`items` tối đa 5, `available` tăng dần rồi `product_id`; `count` là tổng thật.

**GET /api/v1/admin/dashboard/recent-orders**:
```json
{ "as_of": "2026-10-06T03:00:00Z",
  "items": [ { "code": "7K3M9Q2XH4TB", "created_at": "2026-10-06T02:00:00Z", "status": "paid", "grand_total": 350000,
               "payment_method": "vnpay", "payment_status": "succeeded", "item_count": 3 } ] }
```
Đúng tối đa 10 đơn, `created_at` giảm dần rồi `id` giảm dần (id không trả ra). Không có trường cá nhân nào (danh sách trắng trường).

**GET /api/v1/admin/reports/revenue** (khoảng 01/09 tới 30/09/2026):
```json
{ "from": "2026-09-01", "to": "2026-09-30", "as_of": "2026-10-06T03:00:00Z", "granularity": "day",
  "buckets": [ { "bucket_start": "2026-09-02", "gross": 200000, "refunded": 0, "net": 200000, "payment_count": 1 } ],
  "totals": { "gross": 320000, "refunded": 200000, "net": 120000, "payment_count": 2 },
  "by_method": { "vnpay": { "gross": 200000, "refunded": 200000, "net": 0, "payment_count": 1 },
                 "cod": { "gross": 120000, "refunded": 0, "net": 120000, "payment_count": 1 } } }
```
`granularity` là `day` (1 tới 31 ngày), `week` (32 tới 92), `month` (từ 93). `buckets` đủ mọi mốc kể cả mốc 0 (ví dụ 30 mốc cho 30 ngày). Tuần bắt đầu thứ Hai (`bucket_start` có thể trước `from`), tháng bắt đầu ngày 1; mốc đầu và cuối chỉ có phần trong khoảng. Tổng các mốc bằng `totals`, `totals` bằng `/dashboard/revenue` cùng khoảng, tổng hai phương thức bằng `totals`.

**GET /api/v1/admin/reports/orders**:
```json
{ "from": "2026-09-01", "to": "2026-09-30", "as_of": "2026-10-06T03:00:00Z", "granularity": "day",
  "buckets": [ { "bucket_start": "2026-09-01", "total": 7,
                 "by_status": { "pending": 0, "confirmed": 0, "paid": 1, "shipped": 0, "delivered": 5, "returned": 0, "cancelled": 1, "expired": 0 } } ],
  "totals": { "total": 200, "by_status": { "pending": 2, "confirmed": 10, "paid": 20, "shipped": 10, "delivered": 119, "returned": 1, "cancelled": 30, "expired": 8 },
              "cancel_rate": 15.0, "expired_rate": 4.0, "average_order_value": 350000 } }
```
`cancel_rate`, `expired_rate` là phần trăm một chữ số thập phân hoặc `null` khi `total` = 0; `average_order_value` là số nguyên hoặc `null`.

**GET /api/v1/admin/reports/products** (`?sort=units&limit=10`):
```json
{ "from": "2026-09-01", "to": "2026-09-30", "as_of": "2026-10-06T03:00:00Z", "sort": "units", "limit": 10,
  "units_total": 90, "distinct_products": 3,
  "items": [ { "product_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa", "name": "Áo thun", "units_sold": 40, "items_amount": 4000000 } ] }
```
`items_amount` là giá trị hàng bán (giá lúc đặt nhân số lượng), **không phải doanh thu** (DSH-REQ-20261006-105126458 BR2).

## Nguồn dữ liệu
DSH không có bảng và không nhận event ở v1 (ADR-020: phương án A giao diện đọc cộng cache 60 giây; loại B read model và C đọc bảng trực tiếp). `events.md` không còn DSH trong cột Consumers (K-09). Mỗi khối dưới đây lấy dữ liệu qua giao diện đọc nội bộ của module có trong Phụ thuộc của DSH (`architecture.md`: DSH phụ thuộc ORD, PRD, INV, USR, PAY; hàng `DSH` ở bảng "Giao diện module").

| Khối | Cách lấy | Module nguồn | Vì sao không dùng event hoặc read model riêng |
|---|---|---|---|
| Doanh thu, báo cáo doanh thu | giao diện đọc | PAY | Tiền phải khớp PAY (SB-23: số tiền ở báo cáo chỉ lấy từ PAY). DSH không là consumer của PaymentSucceeded, PaymentRefunded; PaymentRefunded vẫn không mang `amount` (V-05 chỉ để SAU khi chuyển read model) và event outbox giao ít nhất một lần nên đếm theo event vẫn lệch khi có lỗi xử lý; đọc thẳng từ PAY (ADR-020) thì khớp tuyệt đối |
| Hoàn tiền thất bại cần xử lý | giao diện đọc | PAY | Là trạng thái hiện tại của hàng đợi hoàn tiền; đếm event RefundFailed sẽ không giảm khi admin đã xử lý xong |
| Số đơn, báo cáo đơn, đơn gần đây, báo cáo sản phẩm | giao diện đọc | ORD | OrderCreated mang `items` nhưng không mang trạng thái hiện tại; trạng thái đơn đổi qua nhiều event (OrderPaid, OrderCancelled, OrderDelivered...) mà DSH không là consumer; ORD là chủ trạng thái (tám trạng thái, có `returned`) |
| Số khách | giao diện đọc | USR (USR gọi AUTH) | AUTH không phát event đổi role hay tạo tài khoản cho DSH; DSH không phụ thuộc AUTH theo `architecture.md`, đường đếm là `USR.countCustomers` gọi AUTH (A-03, ADR-020) |
| Số sản phẩm | giao diện đọc | PRD | ProductActivated chỉ có INV là consumer; số theo trạng thái hiện tại |
| Tồn thấp | giao diện đọc | INV | LowStockDetected chỉ phát lúc đi xuống (cờ `low_stock_notified`, V-07), không báo khi đã nhập lại hàng nên không dựng được danh sách "đang thấp" |

Đánh đổi của giao diện đọc: module chủ phải thêm phương thức tổng hợp (bảng "Giao diện module" đã khai hàng DSH, chữ ký chốt ở tech-design của họ, xem dưới) và truy vấn tổng hợp chạy trên bảng giao dịch; giảm nhẹ bằng bộ nhớ đệm 60 giây, giới hạn 366 ngày, hạn 5 giây. Đổi lại số liệu luôn cùng nguồn với module chủ và không lệch do mất event. Nếu sau này truy vấn tổng hợp quá nặng, dựng read model theo event bằng ADR mới (cần bổ sung consumer ở `events.md` và event bền).

## Giao tiếp giữa module
- **Gọi trực tiếp** (`depends_on: [ORD, PRD, INV, USR, PAY]`, đúng cột Phụ thuộc của DSH ở `architecture.md`): chỉ qua các **giao diện đọc nội bộ** (phương thức trong tiến trình, không HTTP, chỉ đọc). Hợp đồng ở `architecture.md` (bảng "Giao diện module", các hàng `DSH | ORD`, `DSH | PAY`, `DSH | PRD`, `DSH | INV`, `DSH | USR` (R-28)); tên phương thức đã ghi ở bảng đó (R-28), chữ ký chi tiết chốt ở tech-design của module chủ (chưa có ID requirement của họ cho các phương thức này, ghi ở questions.md; DSH không sửa tài liệu của họ). Mọi phương thức nhận khoảng UTC, trả số nguyên VND, không trả trường cá nhân:

| Module | Phương thức đề xuất | Trả về | Khối dùng |
|---|---|---|---|
| PAY | getRevenue(range_utc, bucket?) | totals (gross, refunded, net, payment_count), theo mốc, theo phương thức, trong một câu truy vấn; `refunded` chỉ gồm Refund `succeeded` đã đưa Payment sang `refunded` (PAY xác nhận, xem DSH-REQ-20261006-105125714 BR1) | doanh thu, báo cáo doanh thu |
| PAY | countFailedRefunds() | số Refund `failed` đang chờ admin xử lý (đã hết lượt tự thử lại) | doanh thu |
| ORD | countByStatus(range_utc) | số đơn theo tám trạng thái (có `returned`) | số đơn |
| ORD | getOrderSeries(range_utc, bucket) | số đơn theo mốc và trạng thái, số đơn payment_status succeeded kèm tổng grand_total | báo cáo đơn |
| ORD | listRecent(limit) | đơn mới nhất, không trường cá nhân | đơn gần đây |
| ORD | getTopProducts(range_utc, sort, limit) | dòng đơn nhóm theo product_id của đơn `paid_at` trong khoảng, payment_status succeeded, status không thuộc cancelled, expired, returned | báo cáo sản phẩm |
| PRD | countByStatus() | số sản phẩm theo ba trạng thái | số sản phẩm |
| INV | getLowStockSummary(limit) | count và danh sách tồn thấp kèm tên, sku | tồn thấp |
| USR | countCustomers(range_utc) | total, locked, new_in_range của role customer | số khách |

- **Không gọi** AUTH, CHK, CRT, PRM, SHP, NTF, REV (không có trong Phụ thuộc). Người dùng và role lấy từ phiên qua guard `SessionContext` của platform (ADR-012, A-01; AUTH cung cấp triển khai, AUTH-REQ-20261006-095515918); DSH không khai PRJ hay AUTH ở `depends_on` cho phần dùng chung này.
- **Phát (emits)**: không có. DSH chỉ đọc.
- **Nhận (consumes)**: không có ở v1 (ADR-020). `events.md` không còn DSH trong cột Consumers của event nào (K-09); chuyển sang read model theo event là backlog (V-16) và khi đó mới thêm DSH vào Consumers của PaymentSucceeded, PaymentRefunded (kèm `amount`), OrderPaid, OrderCancelled, OrderExpired.
- **Audit**: ghi `AuditService.record()` (`dashboard.view`) của platform (ADR-021, entity AuditLog thuộc PRJ), gộp một dòng mỗi admin mỗi phút (K-16, SB-19; DSH-REQ-20261006-105126549 BR7). Dấu gộp là bộ nhớ trong tiến trình (xem DSH-DB); audit đi trong giao dịch ngắn riêng, ghi lỗi không chặn xem, chỉ log `error` (ADR-021, SB-19, M-10).
- **Mã lỗi** đăng ký qua `registerProblem` của PRJ, `type` là URN `urn:ecom:error:<code>` (ADR-023): `invalid-parameter` 400, `dashboard-source-unavailable` 503, `rate-limited` 429.
- **Biến môi trường** (kiểm schema zod lúc khởi động, ADR-007): `DASHBOARD_CACHE_TTL_SECONDS` (60), `DASHBOARD_SOURCE_TIMEOUT_MS` (5000), `DASHBOARD_RATE_LIMIT_PER_MINUTE` (30, bậc D của SB-14). [OPEN] PRJ cần nhận ba biến này vào schema chung (nền chưa liệt kê, ghi ở questions.md).
